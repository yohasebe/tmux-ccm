## [Unreleased]

### Added
- `docs/state-machine.md` — formal reference for the detection state machine. State definitions, both detection backbones (legacy `DETECTION_RULES` table and event-log `derive_state_from_events`), priority-ordered rule list, derive's decision tree, key discriminators (event/JSONL freshness comparison, raw=PERMIT precedence, startup pid-age grace), and the heuristic time-window constants with their defaults. Three lifecycle walk-through tables (normal turn, Esc interrupt, silent permission resolution) document the intended behaviour for the most common flows. Linked from CLAUDE.md
- Test invariants for the detection pipeline: new `TestPipelineInvariants` and `TestDeriveInvariants` parametrize over the full input space and assert global contracts (resolved state always in the documented set; raw=SHELL/DOWN always pass through; legacy never emits CONT; pid_present=False always shells derive; raw=PERMIT precedence). Plus three new lifecycle scenarios in `TestLifecycleSequences` covering the day's fix flows. Test count grows 473 → 651 (+178)

### Changed
- Default detection path is now the event-log pipeline (P3b, 2026-04-25). With `CCM_USE_EVENT_LOG` unset, `_event_log_mode()` returns `"auto"` instead of disabled — the same behaviour as `CCM_USE_EVENT_LOG=auto`. State is committed from `derive_state_from_events` whenever it returns a non-None answer; the legacy `DETECTION_RULES` pipeline only fires when derive falls back (empty event log, malformed records, unknown event types, post-`session_end` transient with a live pid). This is the production realisation of the event-log redesign tracked in `project_event_log_redesign`. Justification for flipping the default: the observe-mode roll-out on the same day accumulated 2697 diffs across three active projects under heavy real use (build runs, multi-permission turns, leftover dev servers, mid-tool pauses) and once Option A + A' landed, every B-class disagreement (raw=PERMIT pane while event-log returned IDLE/BUSY/CONT) stopped accumulating — pre-fix 206 such diffs / 22409 s, post-fix 0 / 1324 s despite 6× higher activity. Opt-out for users who explicitly want pre-P3b behaviour: set `CCM_USE_EVENT_LOG=off` (or `0` / `no` / `false` — the parser also treats unknown values as `auto`, so misspellings keep you on the new path rather than silently falling back). Unknown values now resolve to `auto` rather than disabled — opt-in is the conservative side now that the event-log path has the safety nets

### Fixed
- Stuck-PERMIT release on both detection paths. After the user accepts a permission dialog (especially in `accept edits on` mode where `⏵⏵` keeps `raw=BUSY`), Claude Code does not always fire a "permission resolved" hook to clear the PERMIT signal. The dashboard then locks on ⚠ PERMIT — `hook_permit_blocking` (legacy) and the PERMIT branch of `derive_state_from_events` (event-log path) both keep returning PERMIT until a brand-new event arrives. Observed live on monadic-chat 2026-04-26 evening: 5 minutes of phantom PERMIT after permission approval despite a fresh JSONL `end_turn`. Symmetric to the BUSY-axis fix landed earlier in the same release: a new `hook_permit_jsonl_terminal_release` rule (placed before `hook_permit_blocking` in the priority chain) and the same JSONL-terminal-fresher-than-permit-event check in derive's PERMIT branch release stale PERMIT to IDLE when raw is not PERMIT (capture-pane confirms no modal on screen). raw==PERMIT keeps PERMIT — the footer match is the authoritative on-screen-modal signal. Both backbones now recover from silent permission resolution within seconds. New tests: 8 cases — accept-edits stuck path, idle-pane path, fresh-permit skip, derive parametrized over permit_req/notify_permit, raw=PERMIT precedence, stale-jsonl skip, tool_use skip
- Closed the 60 s–600 s stuck-BUSY gap on the legacy detection path. The Esc-fallback in `derive_state_from_events` (above) only fires when `jsonl_age ≤ 60 s`; past that window the legacy `hook_busy_idle` rule held BUSY for the full 600 s `BUSY_HOOK_JSONL_WINDOW` because the Stop hook had not cleared the BUSY signal. Added a new `hook_busy_jsonl_terminal_release` rule before `hook_busy_idle` in the priority chain: when raw=IDLE + hook=BUSY (stale) + JSONL terminal stop_reason within `JSONL_HOOK_GAP_TOLERANCE` (60 s) AND the JSONL terminal is **fresher than the BUSY hook itself** (`hook_after_real_activity_lt=0`), commit IDLE. The hook-fresher-than-JSONL guard prevents the same fresh-prompt false-positive that we already fixed in derive: a new prompt's BUSY hook fires AFTER the prior turn's JSONL terminal, so the rule correctly skips and falls through to `hook_busy_idle`. Symmetric to the event-log path so both backbones recover from Esc-interrupt and hook silence within seconds, not minutes. New tests: 3 cases covering the release path, the fresh-prompt skip, and the tool_use skip
- Esc-interrupt and hook-silence stuck-BUSY recovery in `derive_state_from_events`. When the user presses Esc to interrupt a streaming response, Claude Code does not fire the Stop / StopFailure hook (verified empirically 2026-04-26 against monadic-chat: `[Request interrupted by user]` recorded in JSONL with `stop_reason=stop_sequence`, but no `stop` event ever appeared in the per-project event log). The same silence happens during long upstream-hook outages (anthropics/claude-code#16047 class). In both cases the latest event log entry remains a start-class hook (prompt / pretool / posttool / subagent / compact) and pre-fix derive returned BUSY indefinitely — the dashboard stayed `◉ BUSY` until either the next user prompt or the 10-minute `BUSY_HOOK_JSONL_WINDOW` cap. Post-fix: when the latest event is start-class AND the JSONL `stop_reason` is terminal (`end_turn` / `max_tokens` / `stop_sequence`) AND `jsonl_age` is within `JSONL_HOOK_GAP_TOLERANCE` (60 s) AND **the JSONL terminal is fresher than the latest event** (`event_age > jsonl_age`), derive returns `"IDLE"` directly. The freshness comparison is the critical guard added 2026-04-26 evening: without it, a fresh `prompt` event submitted right after a previous turn ended would falsely flip to IDLE because the JSONL terminal in that case belongs to the prior turn, not the current event (observed live on the teaching pane while Claude was clearly Incubating but the dashboard rendered ● IDLE ✓0s). Returning `None` (defer to legacy) doesn't help here: legacy's `hook_busy_idle` rule holds BUSY off the stale BUSY signal that the missing Stop hook would have cleared, so the dashboard would still report BUSY. `raw=="PERMIT"` keeps precedence — a modal literally on screen is more authoritative than a pre-modal JSONL completion record. Adds `jsonl_age` and `now` parameters to `derive_state_from_events`; defaults (`-1`/`0`) preserve callers that have no JSONL/clock data and want the previous "always BUSY for start events" behaviour. New tests: 21 cases covering parametrized event_type × stop_reason combinations, stale jsonl rejection, tool_use rejection, jsonl_age=-1 sentinel, A' precedence, AND the previous-turn-end regression guard

- Two safety nets for the event-log path so default-on (P3b) is no longer blocked by transient event-log gaps. Both findings came out of the observe-mode roll-out on 2026-04-25 (`project_p3b_observe_validation` runbook). **(A)** When the event log is empty, malformed, of an unknown type, or `session_end` with a live pid, `derive_state_from_events` now returns None instead of silently committing IDLE. The dispatch in `detect_window_state` treats None as "fall back to legacy detection" — the previous IDLE-on-empty behaviour masked a 2.7-hour real outage where the file went temporarily missing while the pane was actually showing a PERMIT modal, which would have let `ccm send` inject keystrokes into a permission dialog. **(A')** The derive function now accepts `raw` (the capture-pane classification) and returns "PERMIT" whenever `raw=="PERMIT"`, regardless of the latest event. The capture-pane footer match is the authoritative signal for modal-blocked panes — the PermissionRequest hook can fire after the modal renders, or fail to fire under #16047-class regressions, leaving the latest event still a start-class hook (pretool/posttool/prompt) when a permission dialog is on screen. raw="BUSY" deliberately does NOT override an event-log IDLE — that is the leftover-dev-server scenario where the legacy process-tree heuristic falsely flags BUSY but the event log correctly says the conversation is done. The `primary` env-var mode also gains None-aware dispatch (it used to commit empty-event IDLE unconditionally, which was the same unsafe pattern). New tests: 16 cases across the derive function and `detect_window_state` dispatch — empty-events + PERMIT modal, pretool-event + PERMIT modal, raw="BUSY" with stop+end_turn (must stay IDLE), session_end + raw="PERMIT" (still None for legacy)

### Changed
- Filter Claude Code v2.1.117 `--continue` startup housekeeping out of JSONL real-activity detection. `permission-mode`, `file-history-snapshot`, and `last-prompt` records carry no `timestamp` field and were being reported as "fresh activity" through the earlier mtime-fallback branch of `_parse_jsonl_tail`. That made `read_jsonl_tail_info` report `jsonl_age ≈ 0` during Claude startup, which in turn made the `jsonl_fresh_activity` rule fire and write BUSY to `@ccm_prev_state` — defeating the `startup_transient_raw_busy` rule and producing the ~10 s of false BUSY reported after every attach to a SHELL window. The three housekeeping types are now in `JSONL_NON_ACTIVITY_TYPES`, and a parseable `timestamp` field is now required for ANY record to be counted as real activity (defense-in-depth for future no-timestamp types)
- Eliminated false BUSY during attach to SHELL windows. Attaching to a SHELL project auto-starts Claude (`claude --continue`); Claude then spawns MCP servers as direct children for 5–30 s before the `❯` prompt renders. `detect_pane_state` sees `has_child=True + no prompt` and returns `raw=BUSY` — identical to a streaming response, so the dashboard flashed BUSY for ~10 s after every attach. A new `startup_transient_raw_busy` detection rule distinguishes this authoritatively by the `claude` process's own age: if raw=BUSY AND no hook signal is present AND the claude pid started less than `STARTUP_GRACE_SEC` (default 60 s) ago, the rule demotes raw to IDLE. The process age is read from the `ps etime` column, a kernel-supplied monotonic value, so the discriminator is not a heuristic. After the grace the rule stops firing; a genuinely hung Claude during startup will surface as BUSY via the normal `raw_not_idle` passthrough. Related: `reset_window_after_attach` no longer wipes `@ccm_prev_state` — the wipe made attached-to-BUSY sessions indistinguishable from startups and no longer serves a purpose now that the startup discriminator is the pid age, not prev_state. Only `@ccm_completed_at` (stale ✓ marker) and `@ccm_shell_history` (cluster canary) are still cleared on attach. Two new Rule condition axes: `hook_missing` (no hook signal present) and `claude_pid_age_lt` (process younger than N seconds), plus `STARTUP_GRACE_SEC` tunable via `CCM_STARTUP_GRACE_SEC`
- Reduced false IDLE flickers during long tool execution, especially under multi-project concurrent load. A new `jsonl_tool_use_pending` detection rule reads the most recent `assistant` record's `stop_reason` from the JSONL tail and holds BUSY as long as it is `"tool_use"` (the authoritative upstream signal that Claude has paused mid-response to await a tool result). The previous 15 s `jsonl_holds_busy` window relied on JSONL mtime freshness alone, which expired mid-tool and left detection at the mercy of a flickering grandchild-process heuristic between tools — exactly the "monadic-chat shows IDLE while Ruby test is running" scenario. `read_jsonl_tail_info()` now returns `(age, stop_reason)` from a single tail parse; `read_jsonl_age` is kept as a thin wrapper for backward compatibility. `stop_reason` of `"end_turn"` / `"max_tokens"` / `"stop_sequence"` still releases BUSY normally; `"tool_use"` is capped at `BUSY_HOOK_JSONL_WINDOW` (600 s) so an abandoned session cannot hold BUSY forever
- Dashboard cursor movement feels smoother under held ↑/↓. The main loop now coalesces contiguous navigation keypresses with a non-blocking `getch` drain (applying each to the selection without re-rendering) and defers the preview-panel redraw during a 100 ms "nav burst" window. Once the burst ends, the main loop triggers a restore render to bring the preview back. Previously each terminal-auto-repeat keystroke paid the full render cost (including character-by-character ANSI-colored preview painting, the single largest per-frame expense), so holding an arrow key accumulated keys in the input buffer and the cursor lagged then jumped
- Refactor: hook scripts share boilerplate via new `ccm_hook_init` / `ccm_hook_format_tool_detail` / `ccm_hook_resolve_project` helpers in `hooks/lib.sh` (−184 lines across 7 scripts)
- Refactor: state icon table centralised in `lib/state_meta.sh`; Python `STATE_ICONS` and the bash `ccm_state_icon` helper read from one source, with a bats parity test enforcing the single-source invariant
- Refactor: state detection engine extracted into `lib/ccm_detection.py` (`DETECTION_RULES`, `Rule` / `DetectionContext` / `Action` types, slow- and fast-path context builders, `apply_actions`). `ccm_core.py` re-exports the detection API so existing callers are unaffected
- Refactor: `cmd_*` subcommand handlers extracted into `lib/ccm_commands.py` (17 handlers, 849 lines). `ccm_core.py` shrinks from ~3000 to ~1750 lines of constants, tmux helpers, and the data model

### Fixed
- Stale-signal recovery for both PERMIT and BUSY axes after a user dismisses a permission dialog with Esc / No / Tab to amend. Two interlocking gaps caused the dashboard to freeze on the wrong state for the full 600 s `PERMIT_MAX_TIMEOUT` / `BUSY_HOOK_JSONL_WINDOW` window even after the modal had been gone for minutes — empirically reproduced 2026-04-24 against a live monadic-chat session via `ccm debug trace`. (1) `fallback_permit_hold` was bounded by `PERMIT_MAX_TIMEOUT` (600 s), but Claude Code fires no follow-up hook when a permission is dismissed without approval, so the PermissionRequest signal stays PERMIT for the full 10 minutes. New `PERMIT_GAP_TOLERANCE` constant (60 s, `CCM_PERMIT_GAP_TOLERANCE`) caps the post-IDLE hold; the longer `PERMIT_MAX_TIMEOUT` is preserved for `hook_permit_blocking`, which only fires while the modal is still visible (`raw in (BUSY, PERMIT)`). (2) After PERMIT released, `jsonl_tool_use_pending` would re-grab the still-`tool_use` JSONL tail and hold BUSY for another 600 s, mirroring the PERMIT-stuck symptom on the BUSY axis. The rule now requires `hook_missing=True` so any present hook signal (PERMIT/SHELL) forces fall-through to `fallback_busy_to_idle`. The genuine between-tools gap (Stop deletes signal → next PreToolUse) still works because the signal IS missing in that case; long-running tools with a live BUSY signal are still held by `hook_busy_idle` (which carries the `hook_after_real_activity_lt` recap-defense guard). Net effect: a dismissed permission resolves to the correct state (IDLE, or whatever Claude is genuinely doing) within `PERMIT_GAP_TOLERANCE` instead of staying PERMIT then BUSY for 20 minutes
- `/model` picker in Claude Code v2.1.119 is now correctly classified as PERMIT instead of BUSY. The modal's footer changed from `Enter to confirm · Esc to cancel` (the verb session-resume still uses, and the one a5534c16 originally added) to `Enter to confirm · Esc to exit`, so the fixed-verb branch of `PATTERN_PERMIT_FOOTER` stopped matching and the dashboard reported BUSY for any pane showing `/model`. The confirm-modal branch now matches `Esc to \w+`, covering both observed verbs plus any future modal-author variant (close / quit / dismiss / ...) without a further regex chase. Verified empirically 2026-04-24 against the live `/model` dialog (BUSY → PERMIT). The `/skills` menu in v2.1.119 uses a different footer (`Enter to use, t to sort, Esc to close`) and remains IDLE as before — it is free-navigation slash menu, not a blocked decision
- Confirmation modals (session-resume from v2.1.117+, `/model` picker, `/exit` confirmation, ...) are now correctly classified as PERMIT instead of BUSY. The session-resume modal specifically shows `❯` as a menu cursor indented by two spaces, so the original `PATTERN_INPUT_PROMPT` (anchored at column 0) did not match, and the footer `Enter to confirm · Esc to cancel` was not covered by the permission-specific `PATTERN_PERMIT_FOOTER`. `detect_pane_state` saw `has_child + no prompt → raw=BUSY`, which is wrong for a modal that is waiting on a single user keypress. The footer pattern now also matches `Enter to confirm · Esc to cancel`, so these modals land on the same PERMIT state as permission dialogs — they share the "Claude blocked, user action required" semantics and the ⚠ icon. Bare `Esc to cancel` footers (slash-menu navigation like `/hooks`) remain non-PERMIT as before
- Phantom "very late" COMPLETED desktop notification: `on-notification.sh` no longer fires `_ccm_instant_notify` on the `idle_prompt` branch. Claude Code's `Notification(idle_prompt)` event has a documented 10–60s+ delay (anthropics/claude-code#5186), and the per-project 10s dedup window was too short to absorb the late echo of an already-sent on-stop notification — the user saw a duplicate alert long after the response had finished. The on-stop.sh grace-scheduled notification (within `CCM_COMPLETION_GRACE_SEC`, default 3) is now the authoritative completion ping. Stop-hook reliability regressions this idle_prompt fallback was guarding against (#16047, #25655) are both fixed upstream. The `idle_prompt` branch still clears the BUSY signal file so the IDLE state transition is unaffected
- `_ccm_instant_notify` now returns 0 on deliberate skip decisions (`@ccm-notify=off`, state not in the configured list, etc.). Previously a bare `return` inherited a failed `[[ ]]` exit status and leaked 1, making "decided not to notify" indistinguishable from an error at the call site. Current hook call sites ignore the return value so production was unaffected, but the new contract is now enforced by the parity test
- Circular-import latent bug: running `python3 lib/ccm_core.py <subcmd>` loaded the file as `__main__`, and the new submodule re-exports triggered a partially-initialized re-entry on `ccm_detection` / `ccm_commands`. Fixed with a `sys.modules.setdefault("ccm_core", ...)` alias at module top; normal `import ccm_core` callers are unaffected

### Added
- `CCM_USE_EVENT_LOG=auto` — new opt-in mode that uses the phase-2 event-log state derivation per-project IFF an event log file exists for that project, and falls back to the legacy `DETECTION_RULES` pipeline otherwise. This is the recommended production setting once you have confirmed hooks are firing for your projects (`ls $TMPDIR/ccm-$UID/hooks/*.events.jsonl`): it gets the new heuristic-free state machine where it can apply, while keeping the existing safety net for projects that have not yet recorded any hook event (newly registered, hooks just installed, or `ccm setup-hooks` skipped). Distinct from the existing `primary` mode, which commits the event-log state unconditionally — `primary` returns IDLE for an empty event log even when Claude is actively streaming, which is wrong unless you are deliberately forcing the new path for diagnosis. Default remains unset (legacy only) to keep this release zero-behaviour-change for users who have not opted in; flipping the default to `auto` is deferred to a later cycle once `observe`-mode runs accumulate enough no-diff data
- `ccm send` now treats CONT as a BUSY-equivalent send target: refused without `--force`, queued into the input buffer with `--force`. The error message names the state explicitly (`"<name> is CONT (tool_use in progress). Claude paused mid-turn awaiting a tool result..."`) so the caller can quote the actual reason back to the user instead of "BUSY by some heuristic". This propagation completes the CONT story for the event-log path: `STATE_PRIORITY` puts CONT in BUSY's slot so dashboard sort ordering is correct, `priority_color` / `priority_icon` group CONT with BUSY in the mode-0 status-right collapsed indicator (so the existing "5,6: BUSY ◉" summary still works without teaching the new state), and CONT gets its own amber color in `TMUX_COLORS` (`#d7af5f`) and the dashboard color pair (xterm-256 179) so per-project rendering in modes 1/2 and the dashboard list visually separates "actively streaming" (BUSY salmon) from "paused mid-tool" (CONT amber). Behaviour is opt-in alongside the rest of phase 2 — without `CCM_USE_EVENT_LOG=primary` the legacy detection pipeline never emits CONT, so steady-state users see no UI change. New tests cover send refusal/force, priority-table sorting, and the inject_status grouping
- Event-log redesign phase 2 (parallel state derivation, opt-in via env var, still no default behaviour change). A new pure function `derive_state_from_events(events, jsonl_stop_reason, pid_present, claude_pid_age)` resolves state directly from the per-project event log written in phase 1, plus the JSONL `stop_reason` and process-tree presence — the entire state machine collapses to a single readable function with `STARTUP_GRACE_SEC` as its only time-window heuristic (down from the legacy pipeline's five). Activation gate is the `CCM_USE_EVENT_LOG` env var: unset = legacy only (default), `observe` = compute both paths and log the diff to `CCM_DEBUG_TRACE` while still committing the legacy state, `primary` (or `1`/`true`/`yes`/`on`) = commit the event-log state. The new `CONT` state ("continuation": Claude paused with `stop_reason="tool_use"` and no follow-up hook yet) lands in `STATE_ICONS` with the `◍` glyph and is added to `state_meta.sh` for bash parity, but only the event-log path emits it — legacy detection cannot produce CONT. The phase-2 event-log reader (`read_events_tail` in `ccm_core.py`) shares the tail-read + (mtime, size) bounded-cache pattern of `_parse_jsonl_tail`, parses the last 8 KB / 200 lines newest-first so the parse cap keeps recent records, and silently skips malformed lines so detection never hard-errors on schema drift. `_trace_scan` now emits `event_log_state` and a `diff:true` flag on disagreement so `jq -c 'select(.diff)'` isolates the rows where the two paths would have produced different answers. With this in place phase 3 can switch the default and shrink `DETECTION_RULES` to a fallback for hook-less projects. New tests: 50+ pytest cases covering the reader (cache hit/invalidate, tail truncation, malformed-line tolerance, limit slicing) and the derive function (every event class × stop_reason combination, lifecycle scenarios from `project_false_idle_long_tool` and `project_event_log_redesign`, indefinite PERMIT, iterator inputs)
- Event-log redesign phase 1 (detection lays the foundation, no behaviour change). Every Claude Code hook now appends one JSONL record to `$HOOK_DIR/<md5-of-cwd>.events.jsonl` alongside writing the legacy signal file — the authoritative timeline that phase 2+ will derive state from as a pure function of events (replacing the five time-window heuristics with a single `STARTUP_GRACE_SEC` pid-age discriminator). Schema: `{"ts": unix_seconds, "type": <normalized>}` where `type` is drawn from a 9-member vocabulary (`prompt`, `pretool`, `posttool`, `subagent`, `compact`, `stop`, `permit_req`, `notify_permit`, `notify_idle`, `session_end`). The shared `on-pre-tool-use.sh` script dispatches on the upstream `hook_event_name` so PreToolUse / PostToolUse / SubagentStart / PreCompact land in their own buckets rather than a blended "pretool" lump. New helpers in `hooks/lib.sh`: `ccm_append_event` (POSIX O_APPEND, <4KB atomic, silent on write failure so the legacy path always runs) and `ccm_hook_event_name` (extracts the upstream event name from the JSON payload). Events are cleaned up by `cleanup_project_runtime_files` alongside the existing signal files so nothing leaks when a project is unregistered. Detection logic is unchanged in this phase — the current `DETECTION_RULES` pipeline reads no event log state — so this commit is a no-op for steady-state users while giving phase 2 a stable upstream signal to consume. New bats suite `tests/test_event_log.bats` (20 tests) covers the writer, the hook_event_name extractor, and end-to-end event-type dispatch for every hook script, plus two regression guards that verify the legacy BUSY/PERMIT signal-file behaviour is intact
- `ccm send` now annotates its PERMIT refusal with modal classification, human-readable guidance, and a captured pane tail. When Claude A tries to message Claude B and B is in PERMIT state, the refusal text used to be a single generic line — Claude A could neither tell the user what kind of modal was blocking B nor suggest how to resolve it. A new `classify_permit_modal()` inspects the captured tail and distinguishes four categories: `session-resume` (claude --continue resume picker, safe), `permission-request` (tool permission dialog, dangerous to auto-dismiss), `confirmation-modal` (/model picker, /exit, ... — safe but user-decision), and `unknown-permit` (fallback for future modals). Each category has a tailored guidance block embedded in the error output, and the last 8 non-empty lines of the pane are appended so the caller can quote the actual modal text to the user. PERMIT refusal remains unconditional — even `--force` cannot bypass it — but the caller now has enough information to explain the situation without peeking into the target pane. Three new patterns (`PATTERN_RESUME_MODAL`, `PATTERN_PERMISSION_DIALOG`, `PATTERN_MODEL_PICKER`) sit alongside the existing `PATTERN_PERMIT_FOOTER` and are checked in priority order (most-specific first); permission dialog always wins over any ambiguous footer. Non-goal: no automatic dismissal of any PERMIT modal from another pane — misclassifying a permission dialog as a "safe" confirmation would be a correctness disaster, so the user always handles PERMIT manually
- Phase metadata on every detection rule (step 1 of a phased move toward a phase-scoped evaluator). Each `Rule` now carries a `phase` field (`shell` / `startup` / `midturn` / `between_tools` / `idle` / `permit`, or `None` for genuine catch-all passthroughs like `raw_not_idle` and `default`). The phase is surfaced in both `ccm debug trace` (`rule_name[phase]` in the output column) and `CCM_DEBUG_TRACE` (new `"phase"` field in the JSONL), so "why did this rule fire?" investigations see the intended session-lifecycle scope without a separate rule→phase lookup. The evaluator is unchanged at this step; two drift-guard tests assert every rule has a phase (or is explicitly listed as a passthrough) and that the classification matches a documented mapping. See `project_phase_machine_roadmap` memo for the step 2 plan
- `ccm debug trace <project> [interval]` — live, read-only tracer for state detection. Prints one line per scan showing every `DetectionContext` input, the matched rule, and the resolved state, so that "why did this flash BUSY for 10 s after attach?" bugs can be correlated with the rule-firing sequence without spinning up instrumentation. Does not write to `@ccm_prev_state`, so it can run alongside the normal detection pipeline. Defaults to 0.3 s interval, Ctrl-C to stop
- `CCM_DEBUG_TRACE=/path/to/log` env var — when set, the main detection pipeline (`inject_status`, dashboard, `ccm status`, ...) appends a JSON-per-line record per scan cycle with every context field plus the matched rule and resolved state. Useful for post-hoc debugging of "it happened once yesterday"-type reports. Pair with `jq -c 'select(.target=="0:N")'` to slice by project. Writing is best-effort; a broken trace file never blocks detection. The log auto-suspends at `TRACE_MAX_BYTES` (default 100 MB, tunable via `CCM_TRACE_MAX_BYTES`); at the threshold a single `{"event":"trace_cap_reached", ...}` sentinel is written and subsequent appends are silently skipped so a forgotten trace cannot exhaust disk space. Use `tmux set-environment -g CCM_DEBUG_TRACE <path>` (not shell `export`) so the tmux-spawned `inject-status` subprocess inherits the variable
- `CCM_TRACE_ONLY_DIFF=1` env var — restricts `CCM_DEBUG_TRACE` writes to rows where the legacy and event-log derivations disagree (i.e. the existing `diff:true` filter, applied at write time instead of at `jq` time). Designed for long observe-mode runs: a busy multi-project tmux can produce ~100 records/sec of agreement noise that wastes disk and trips `TRACE_MAX_BYTES` within an hour, while the rows that actually matter for P3b validation are only the diffs. With this flag set the file stays empty until a real disagreement shows up, so observe-mode can run for days. Has no effect when `CCM_USE_EVENT_LOG` is unset (no event-log state to diff against, so no rows would ever pass the filter). Accepts the same truthy values as `CCM_USE_EVENT_LOG` (`1` / `true` / `yes` / `on`)
- Drift guard: `tests/test_notify_parity.bats` (15 rows) verifies Python `notify()` and bash `_ccm_instant_notify` reach identical fire/skip decisions for every `@ccm-notify` × state combination. PATH-override sandboxing; no production code is touched

## [0.2.0] - 2026-04-18

Initial public release.

### Added
